ServeProof · UX brainstorm · 2026-08-16

PAYOUT_GAP을
“해결 가능한 일”로 바꾸기

노동자에게 불일치를 보여주는 데서 끝내지 않고, 사업장 급여 담당자에게 확인을 요청하고 답변과 지급 완료까지 한 화면에서 추적하는 흐름.

TL;DR — CTA는 “사업장에 지급 확인 요청”이 가장 자연스럽다. 단순 이메일 전송이 아니라 ServeProof 안에 요청 레코드를 만들고, 이메일은 그 요청을 알리는 전달 수단으로만 사용한다.

현재 상태

경고는 유형과 설명만 보여준다. 사업장, 날짜, 금액, 대기 기간, 다음 행동이 없어 노동자가 화면을 본 뒤 다시 전화·문자·이메일로 문제를 풀어야 한다.

현재 ServeProof: 감지는 하지만 해결 루프는 열리지 않는다.

추천안: 요청 → 확인 → 해결

지급 대기 감지→확인 요청 보냄→사업장 확인 중→지급됨 / 설명 받음
지급 확인이 필요해요 $118.00 Demo Diner · 8월 15일 근무 · 승인 후 3일째 승인된 팁 배분이 아직 지급 기록과 연결되지 않았습니다. 사업장 급여 담당자에게 금액과 근무일만 포함한 확인 요청을 보낼 수 있어요. [ 사업장에 지급 확인 요청 ] [ 시프트 상세 보기 ]

문구 원칙: “미지급”, “체불”을 시스템이 단정하지 않는다. 지급 데이터 지연이나 매칭 실패 가능성이 있으므로 “지급 기록이 아직 확인되지 않음”을 기본 표현으로 쓴다.

아이디어 우선순위

1지급 확인 요청 MVP

버튼을 누르면 사업장·근무일·승인 금액이 미리 채워진 확인 모달을 연다. 노동자는 선택 메모만 더하고 발송한다.

받는 곳 Demo Diner 급여 담당자 근무일 2026-08-15 승인액 $118.00 메모 [선택] [ 요청 보내기 ]

2요청 상태 추적 MVP

발송 직후 CTA를 없애고 “8월 16일 요청 보냄”과 다음 상태를 보여준다. 반복 클릭과 불안을 동시에 줄인다.

  • OPEN 요청 보냄
  • ACKNOWLEDGED 사업장 확인 중
  • RESOLVED 지급 확인됨
  • CLOSED_WITH_NOTE 설명과 함께 종료

3사업장 액션 인박스

매니저 화면에는 일반 알림이 아니라 담당자·기한·대화가 있는 작업으로 들어간다. “지급 처리”, “이미 지급됨”, “정보 요청” 중 하나를 선택한다.

4단계적 재알림

첫 요청 이후 즉시 재전송하지 않는다. 48–72시간 쿨다운 뒤에만 “한 번 더 알림”을 제공하고, 응답이 없으면 요청 타임라인을 내려받게 한다.

교차 도메인에서 가져올 패턴

결제 진행 트래커

결제 제품처럼 “무슨 일이 일어났고 다음 단계가 무엇인지”를 순서로 보여준다. PAYOUT_GAP에도 감지·요청·확인·지급 단계를 적용한다.

지원 티켓의 대화

이메일을 보내고 끝내지 않고 요청 내용, 답변, 상태 변경을 하나의 스레드에 쌓는다. 담당자가 바뀌어도 맥락이 남는다.

환불 상태 타임라인

금액과 이벤트 타임라인을 한 화면에 묶는다. 노동자가 “얼마가, 언제부터, 어디에서 멈췄는지” 바로 이해하게 한다.

구현 시 중요한 데이터 설계

  • 알림 ID에 요청을 직접 묶지 않는다. 현재 재계산은 미해결 경고를 삭제 후 재생성하므로 ID가 안정적이지 않다.
  • 요청 키는 최소 workerId + venueId + shiftId + type. 열린 요청이 있으면 새 요청 대신 기존 상태를 반환한다.
  • 수신자는 임의 이메일이 아니라 해당 사업장의 OWNER / MANAGER / PAYROLL_ADMIN 멤버다.
  • 이메일에는 전체 소득 보고서를 넣지 않고 사업장명, 근무일, 승인 금액, 요청 링크만 넣는다.
  • 발송·확인·답변·해결 이벤트를 감사 로그로 남긴다. 이메일 실패가 요청 레코드 생성을 되돌리지 않도록 재시도 가능한 전달 상태를 둔다.

와일드 카드: 조용한 합의 창

노동자가 사업장에 요청하기 전에 24시간 “조용히 기다리기”를 선택하면, ServeProof가 예정 지급 데이터가 들어오는지 감시한다. 들어오면 알림 없이 자동 해결하고, 안 들어오면 요청 버튼을 다시 강조한다. 데이터 동기화 지연으로 생긴 불필요한 긴장을 줄일 수 있다.

결론

첫 버전은 알림 카드 상세화 + 지급 확인 요청 + 발송 상태 + 사업장 인박스까지가 적절하다. 이메일은 채널이고, 제품의 핵심은 양쪽이 같은 요청 상태와 타임라인을 보는 것이다.
